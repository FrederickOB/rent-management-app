## 4. Design

### 4.1 Modules

- **`portfolio` (new, layer 3):**
    - Owns portfolios, properties, ownership, blocks, units, codes, availability, bands, meters and amenities.
    - Also owns property photos and papers, and the import.
    - Imports `companies`, `documents`, `rules`, `audit` and `policy`; `MODULE_MAP` in the lint config gains the entry.
- **`companies`:**
    - Gains owner records; the architecture's module map already gives owners to `companies`.
    - Property ownership stays in `portfolio`, which imports `companies`.
- **`policy`:**
    - Gains the M2 actions and `scopeFor(actor)`.
    - Gains the transaction setting that the scope predicate reads (4.4).

### 4.2 Tables

All tables share these properties:
- **RLS and audit:** each table has company RLS, composite foreign keys and audit triggers, through the M1 helpers.
- **Scope column:** each table carries `property_id`, so the scope predicate filters without joins. Composite foreign keys keep it consistent with the parent rows.
- **No deletes:** `rent_app` has no DELETE on `property`, `block`, `unit` or `meter`. Archiving keeps the codes taken.

| Table | Mutability | Purpose |
| --- | --- | --- |
| `owner` | Mutable, row-audited, archived rather than deleted | AD-02: an agency's client, or the landlord in their own company. Stores:<br>• kind (individual or company; joint and family are reserved for PR-07);<br>• name, a short reference for imports and lists, phone and email;<br>• country and time zone of residence, for owners abroad;<br>• notes. |
| `portfolio` | Mutable, row-audited | PR-01 grouping. Every company gets a "Main portfolio" automatically, so a landlord with one never has to think about it. |
| `property` | Mutable, but the code is fixed once the first unit exists. Row-audited, archived. | PR-01, PR-03:<br>• code, name and type (apartment block, house, compound house, shop, office, warehouse, mixed-use building, gated estate);<br>• use (residential, commercial, mixed);<br>• address, map pin, and where the address came from (lookup or manual). |
| `property_ownership` | Append-only | AD-02, PR-07-ready. **Country data.** The `country` table gains a list of regions; Ghana's has its 16 regions. Another market then brings its own list without code changes (NFR localisation).

### 4.3 Unit codes (decision 1)

- **Format.** `AREA-PROP-BLOCK-UNIT`, for example `ACC-LEG-B2-04`.
    - Letters A–Z and digits only within each part, stored in capitals.
    - Each part has a maximum length, so a full code is at most 18 characters.
- **Property code.** The area and property parts are chosen when the property is created; the screen suggests them from the town and name.
    - They are unique within the company.
    - They are fixed once the first unit exists.
- **Block and unit parts.**
    - A block code is unique within its property, and a unit label is unique within its block.
    - Bulk creation numbers units after the highest number ever used in that block, archived units included.
- **Collisions.** A code that is already taken is refused with a free alternative suggested; codes are never renumbered silently.
- **Database guards:**
    - a unique index on `(company_id, code)` covers all rows, archived ones included;
    - triggers refuse any change to a code;
    - with no DELETE privilege, a code can never be reused.
- **Payment references** belong to leases (prd-issues 15; built in M4a). Unit codes appear beside them on invoices and receipts.

### 4.4 Permissions and scope (AD-02, AD-03)

**New actions.** `owner.view`, `owner.manage`, `register.view`, `register.manage`, `register.import`, `unit.band_override`, `property_photo.view`, `property_paper.view`, `property_file.upload`.

| Action | Owner, own company | Owner, agency client | Agency admin | Manager | Accountant | Caretaker | Adviser |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `owner.view` | ✓ | own record | ✓ | ✓ | ✓ | – | scoped |
| `owner.manage` (create, edit, archive, change ownership) | ✓ | – | ✓ | – | – | – | – |
| `register.view` (properties, blocks, units, meters, history) | ✓ | scoped | ✓ | ✓ | ✓ | scoped | scoped |
| `register.manage` (create, edit, archive, availability, meters) | ✓ | – | ✓ | ✓ | – | – | – |
| `register.import` | ✓ | – | ✓ | ✓ | – | – | – |
| `unit.band_override` | ✓ | – | ✓ | – | – | – | – |
| `property_photo.view` | ✓ | scoped | ✓ | ✓ | ✓ | scoped | scoped |
| `property_paper.view` (decision 4) | ✓ | scoped | ✓ | ✓ | ✓ | – | scoped |
| `property_file.upload` | ✓ | – | ✓ | ✓ | – | – | – |

**Why some rights are narrow.**
- **Band overrides** are limited to owners and agency admins, because a band sets the subscription rate (PB-01). A manager could otherwise lower the bill.
- **Owner records** are managed by owners and agency admins. Onboarding a client is an agency decision.

**Scope.** M1's membership `scope` (owners, properties) now takes effect:
- **Required scopes.** An agency-client owner or an agency adviser must have at least one owner, and a caretaker at least one property. A manager may be scoped or unscoped.
- **Resolving the scope.** `PolicyService.scopeFor(actor)` returns either "everything" or a set of property ids. The set is the current properties of the actor's owners plus any properties assigned to the actor.
- **Defence in depth** (architecture section 11):
    - each request transaction sets `app.property_scope`, where NULL means everything;
    - the register tables get a second, restrictive RLS policy: `app.property_scope() IS NULL OR property_id = ANY(app.property_scope())`;
    - `owner` gets the same policy, keyed on owner id;
    - a query that forgets the scope filter therefore still returns nothing outside the scope.
- **Order of steps.** The scope is computed at the start of the transaction, before the setting is applied. The users screen gains owner and property pickers to set it.

### 4.5 Unit types and billing bands (PR-02, PB-01)

| Unit type | Default band (PRD section 21) |
| --- | --- |
| single room, chamber and hall, single room self-contained | single room |
| studio, apartment (1 to 5 bedrooms), detached house, semi-detached house, townhouse | self-contained flat or house |
| shop, store, office, warehouse, kiosk | commercial |

- **Overriding a band.** An owner or agency admin can override a unit's band, giving a reason of at least 10 characters. The reason goes into the audit log. Section 21's own examples are the cases this covers:
    - a kiosk-style room let for living becomes a single room;
    - a room let for business use becomes commercial.
- **Changing the type** resets the band to the new default unless the override is confirmed again.
- **Where it lives.** The mapping is product configuration, not law, so it is code in `packages/domain/portfolio`, tested against the section 21 table.

### 4.6 Addresses (PR-03, decisions 2 and 3)

- **GhanaPost GPS.**
    - Input is normalised: capitals, single hyphens between groups.
    - It is checked against the digital-address pattern from M1's adapter (`^[A-Z][A-Z0-9]-\d{3,4}-\d{4}$`, OQ-23).
    - The pure check moves into `packages/domain`, so the form, the import and the adapter share it.
- **Other address fields.**
    - Region comes from the country's list.
    - District, MMDA, town or locality, and street or landmark are text.
    - Location filters use the region, district and property.
- **Lookup.** `GET /address-lookup?code=` goes through `AddressLookupPort` and fills in the region, district and pin for the user to review.
    - If the adapter is missing, down or finds nothing, the form says so and keeps manual entry.
    - The property records which way the address was entered.
- **Map pin.**
    - Latitude and longitude to 6 decimal places, with range checks.
    - Shown as an "Open in maps" link.

### 4.7 Photos and papers (PR-04, decision 4)

- **Uploads.** M1's presigned uploads gain two purposes:

    | Purpose | Types | Size limit |
    | --- | --- | --- |
    | `property_photo` | JPEG, PNG, WebP | 10 MB |
    | `property_paper` | PDF, JPEG, PNG | 20 MB |

- **Photos.** The worker re-encodes each photo with sharp into two versions, a display version (at most 1,600 px) and a thumbnail (400 px).
    - All metadata is removed, location included.
    - The original is discarded once both versions exist, because it may carry GPS coordinates.
- **Papers** are stored as uploaded in the private, versioned `files` bucket. They are reference copies, not signed evidence.
- **Downloads.** Each download needs a policy check on scope and category, and is served by a 5-minute presigned link.
    - PDFs open in the phone's browser.
    - Lists show thumbnails, so a property page stays light on 3G.
- **Removing a file** archives the link; the stored file and its `document` row stay.

### 4.8 Unit status (PR-06; PB-09 groundwork)

- **Availability** (`unit.availability`) is available (the default), reserved, under repair or not lettable.
    - Manual changes follow the architecture's unit status machine, passing through available.
    - Each change writes a `unit_status_event` row (from, to, reason, actor, time) in the same transaction.
- **Occupancy** is neither stored nor settable.
    - A check constraint keeps "vacant" and "occupied" out of availability, and no endpoint sets occupancy.
    - In M2 every unit shows as vacant unless its availability says otherwise.
    - M3 derives occupancy from leases and logs each change in the same history.
- **Status shown:** occupied (from M3), reserved, under repair, not lettable or vacant. An occupied unit under repair shows a badge (prd-issues 21).

### 4.9 Excel import (PR-08)

- **Template.** A generated `.xlsx` file with three sheets:

    | Sheet | Contents |
    | --- | --- |
    | Properties | Property code, name, type, use, owner reference, GhanaPost GPS, region, district, MMDA, town, street or landmark, latitude, longitude |
    | Units | Property code, block code, unit label (blank takes the next number), type, bedrooms, amenities, floor, electricity and water meter numbers and types, availability |
    | Lists | The allowed values, plus the company's owner references |

- **Flow:**
    1. Upload through a presigned link: `.xlsx` only, at most 5 MB and 5,000 unit rows.
    2. The `portfolio.import-validate` job parses and checks every row. It applies the domain rules and the database lookups: existing codes, owners and duplicates within the file.
    3. The report shows how many properties and units will be created, updated or left unchanged, and every error by sheet, row and column.
    4. Commit is allowed only when there are no errors.
    5. The `portfolio.import-commit` job applies the whole import in one transaction, audited, and records the outcome.
- **Idempotent re-import.**
    - Rows match existing records by property code and unit code, or by property, block and label.
    - Unchanged rows are skipped, and changed editable fields are updated.
    - An import never changes a code and never deletes anything.
    - Importing the same file again changes nothing. A validated import committed twice runs once: the commit job's key is the import id plus the check it follows, and the commit locks the import before it applies anything. An import checked again after a failed commit can be committed again.
- **Scope.** Both jobs run with the scope of the person who started them (AD-02), so a manager limited to some owners can import only those owners' properties.
- **Safety.**
    - The file is parsed in the worker, not the API.
    - It is refused if it exceeds size limits, row limits or its uncompressed size, which guards against zip bombs.
    - Only cell values are read; formulas are never evaluated.

### Deviations from this plan

1. **An import row needs a unit label.** Plan 4.9 said a blank label takes the next number. With blank labels, importing the same file twice would add the units twice. A required label keeps re-import idempotent.
2. **A property code is fixed from creation,** not once its first unit exists (plan 4.2).
3. **Invites carry no scope.** M1's invite flow is unchanged. A caretaker, client owner or adviser sees nothing until an admin sets their access on the users screen. The API refuses to save an empty required scope.
4. **Caretakers sign in to the web app with a phone code** (AD-06). M1 built phone sign-in only in the tenant app, which left caretakers no way into the web app.
5. **API shape.** The endpoints differ from 4.10 as follows:
    - the pickers' data, portfolios included, comes from `GET /register/options`;
    - a property's meters and a unit's history come with their details;
    - an owner change is `POST /properties/:id/ownership` with a date, since ownership is history;
    - bulk units are `POST /blocks/:id/units`;
    - meters can be archived.
6. **Error details.** When a property code is taken, the error's details carry a free code, which the wizard offers.
7. **Upload limits live in the domain package** (`packages/domain/src/portfolio/uploads.ts`). The contracts, the services and the API share them.
8. **The import jobs changed in the review** (S3 and M1), as plan 4.9 now describes:
    - the commit key is the import id plus the check it follows;
    - both jobs carry the person's scope;
    - a job that fails its last retry marks the import failed.
    The job catalogue in `docs/architecture.md` is updated.
9. **A request creates at most 5,000 units.** The review triage proposed 1,000. But `PR-01 portfolio list` creates its 5,000 units in one request, and 5,000 matches the import's row limit.
10. **Found during the build and fixed:**
    - rows with problems of their own now have their references checked too;
    - raw queries returned timestamps as text;
    - the current-owner lookup on the portfolio list was rewritten, and now takes about 30 ms;
    - the API now enforces the scope each role needs.

### Deferred

From the review:
- **S5, same-day owner corrections.** Ownership is recorded from today, and a change must be dated after the last one. A property filed under the wrong owner therefore stays visible to that owner's users until the next day. The fix needs a way to supersede an ownership row on the same date, which is a schema change. It should land before M4a, which refuses owner changes once a property has ledger entries.
- **S8, idempotent writes.** A request retried after its response was lost runs twice. Examples: "add 6 units" on 3G, or creating an owner without a reference. The fix is an idempotency key on API writes, a change across the API. I suggest M4a, where cash receipts need the same.
- **N1.** `today()` uses Africa/Accra rather than the company's time zone, while the current-ownership view uses the database's date. This has no effect while every company is in Ghana.
- **N6.** Meter numbers are unique with the supplier's case, but the import compares suppliers lower-cased, so "ECG" and "ecg" duplicates can exist.
- **N7.** Whether an address came from the lookup or was typed is taken from the client. The import no longer rewrites it.
- **N9.** `upload_intent_id` has no foreign key on `property_file` or `register_import`.
- **N10.**
    - Untested: the lookup adapter's failure path, link expiry, and before-and-after audit beyond owners and bands.
    - The files of an archived property can still be downloaded by people allowed to see them.
- **N11.** `defaultPortfolio` writes during GET requests.

### Open items

1. **S6, band overrides and unit type (your decision).**
    - **Today:** when a manager changes a unit's type, the band resets and an owner's or admin's override is cleared. A manager can therefore lower a band they may not override.
    - **Recommended:** keep an override through type changes, so only an owner or agency admin can clear it.
    - **Why it waits:** `PB-01 billing bands` in `packages/server/test/register.int.test.ts` asserts today's behaviour.
2. **S15, extra properties for a client owner (your decision).**

    - **Why it waits:** `AD-02 required scopes` asserts today's rule.
3. **Scoped staff and new owners.** A manager limited to some owners can add an owner record, but cannot see it until an admin adds it to their access. The options are to refuse owner creation to scoped people, or to add the new owner to their access, which is an audited permission change.
