## 4. Design

### 4.1 The onboarding workbook

- **One screen,** `/onboarding`, for company admins and unscoped managers. Scoped staff and caretakers never see it.
- **Each step reuses PR-08's machinery:**
    - `read-excel-file`, the zip guard and the 5 MB limit;
    - a generated template with a Lists sheet for dropdowns;
    - a validate job that writes a report with create, update and unchanged counts and issues by sheet, row and column;
    - commit only with zero issues;
    - one transaction per commit, keyed on the import and its validation;
    - the file's SHA-256 recorded.
- **Matching, so re-importing the same file changes nothing:**
    - owners by reference;
    - units by code;
    - tenants by phone (E.164) within the company, or by name and TIN for a company tenant;
    - leases by unit and start date.
- **Leases** are recorded as paper leases (M3 decision 7). Billing starts at the first rent period on or after the cut-over. A unit with an active lease refuses a second one.
- **Order:** step 2 needs the units from step 1, and step 3 needs every lease it names.

### 4.2 Opening balances (P25)

- **The Balances workbook:**

  | Sheet | Columns |
  | --- | --- |
  | Arrears | lease, period start, kind (rent or service charge), amount, due date |
  | Advances | lease, amount or paid-through date |
  | Deposits | lease, amount held |
  | Withholding | lease, amount, withheld on, period |
  | Owner items | owner, agent-held cash, rent tax outstanding, its due date |

- **Representation:**
    - an invoice kind `opening`, and a payment and allocation source `opening_balance`;
    - an opening payment issues **no receipt**, so it never uses a receipt number. It is not money received through the platform;
    - opening lines are accrued at commit (1100 against 3900), so the daily accrual skips them.
- **Posting:**
    - the rule lives in `packages/domain/src/ledger/opening-posting.ts`: event in, lines out, property-tested;
    - `LedgerModule` posts it through `PostingService`;
    - keys: `P25:<batch>:<item>`;
    - dimensions as usual: property, unit, lease, tenant, invoice line, payment.
- **Dates:**
    - the value date is the cut-over;
    - the accounting date is the cut-over's period, or the open period if that one has since been locked.
- **Tax:**
    - opening payments sit outside the M5 rent tax walk;
    - a receipt after the cut-over that pays opening arrears is taxed on the rent it covers, as any other.
- **Statements:** the first owner statement shows opening balances as their own section.
- **Adjustments** use signed amounts:
    - lowering arrears credits the opening line, refused below what has been paid;
    - lowering an advance or a deposit is refused below what has been drawn;
    - raising adds an opening item.

### 4.3 Pilot metrics

- **The added metrics** are pure functions in `packages/domain/src/reporting/gate1.ts`, rolled up daily with the others into `metric_daily`.
- **Active days** go in `staff_active_day`: company, user and day, written at most once per user per day (cached in memory).
- **WhatsApp adoption** reads the consent records, inbound messages and read receipts.
- **The platform page** gains targets, a trend over the pilot months and an Excel export. The company card shows the same targets.

### 4.4 Data protection

- **The register** is on the tenant page and under Settings → Data protection, for company admins.
- **The export:**
    - rendered by a job, stored write-once, downloaded through a short-lived link;
    - only that tenant's records;
    - it never logs its contents.
- **Anonymisation:**
    - one function per category of record, each checking its retention rule;
    - financial records keep their amounts and references, and lose only the personal fields;
    - the audit chain still verifies afterwards, because audit rows store only "changed" for these columns.
- **Retention review:** a nightly job, listed in the console.

### 4.6 Performance

- **Lighthouse:** `@lhci/cli` in the e2e job, with one config for links and one for the tenant web app.
    - The tenant app's signed-in pages sign in through the fake one-time code in a Lighthouse login script.
    - The 3G profile moves into one shared helper, used by the Playwright specs too.
- **Trimming the tenant app:**
    - libphonenumber's minimal metadata (Ghana and the few countries we accept);
    - async routes on web;
    - a check of what else is in the bundle.
- **Load test:**
    - k6 scripts in `load/`;
    - a fixture builder that extends `perf-fixture.ts` with 50 staff, 5,000 tenants and invoices due at month end;
    - `pnpm load:month-end`, which runs only against a scratch database;
    - results go to a JSON file and a summary, kept as CI artifacts;
    - it also measures audit head-lock contention (M1) and month-end balance reads, which settles whether balance snapshots are needed (M4a).

### 4.7 Resilience

- **The fake provider's switch,** `_test/outage`, can make it:
    - refuse charges with 503;
    - answer slowly or time out;
    - stop sending webhooks;
    - drop them.
- **Drills,** each an integration test and a runbook section:
    - **provider down:** the pay page shows the manual instructions and raises one alert, and no intent is left stuck. When the provider is back, pending checks complete and late webhooks are processed;
    - **webhooks lost:** the five-minute verify and the daily reconciliation recover every payment;
    - **replay:** replaying every webhook of a day changes nothing;
    - **backlog:** the worker is stopped, month-end work is queued (5,000 invoices, reminders, 1,000 webhooks), and the worker is restarted. The drill measures the drain time and checks there are no duplicates.
- **The console's system health page** gains:
    - webhook and dead-letter lists with replay and retry;
    - each queue's oldest job age;
    - the worker heartbeat.
- **Health endpoints:** web gets `/health`, and the api gets `/health/worker`.

### 4.8 Backups

- The checks call the same functions the nightly jobs use.
- A workflow, `.github/workflows/scheduled.yml`, runs monthly and on demand. It holds the drills and the load test.

### Identity

1. **Client addresses (R3 F1, R1 F1).**
    - Fastify's `trustProxy` is the new `TRUSTED_PROXIES` list (addresses or CIDRs). Unset, X-Forwarded-For is ignored.

    - Wrong passwords are also limited per account: 10 in 15 minutes from any address. The key is an HMAC of the email, and only failures count.
2. **Phone codes (R1 F2).**
    - Each attempt is counted by one atomic update before the code is compared. A sixth attempt, or 20 parallel guesses, finds the code dead.
    - Daily caps per phone, each alerted once: 10 codes sent (429 `DAILY_CODES_EXCEEDED`) and 15 wrong codes (403 `DAILY_ATTEMPTS_EXCEEDED`). The per-code limit keeps `TOO_MANY_ATTEMPTS`, and the 15-minute send limit keeps `TOO_MANY_CODES`.
3. **Step-up TOTP (R1 F4).**
    - The attempt is counted atomically before the comparison. After 5 wrong codes in 15 minutes, the step-up locks until the window ends.
    - Each failure is audited as `approval.step_up_failed`, without the code; the lock raises `auth.step_up_locked`.
    - A code's time step is recorded in `two_factor.last_totp_step`, and a step already accepted is refused.
    - The request's state (the cooling-off) is now checked before the code, so a code tried too early is not spent.
    - **Accepted gap for the pilot (founder, 2026-11-10):** sign-in TOTP codes can still be used twice within their window. A replay also needs the password.
    - **M12 plan:** e2e signs in once per person and reuses the session; then the guard is switched on for sign-in too.
4. **Account events audited (R1 F5).**
    - Sign-in now records a keyed hash of the address and the user agent.
    - New events:

        - `auth.signed_out`;
        - `auth.password_set` (`via`: invitation or reset) and `auth.password_changed`;
