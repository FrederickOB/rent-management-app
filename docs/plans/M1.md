```
                      test database harness
packages/server       NestJS modules shared by api and worker: core, identity, audit, rules,
                      documents, policy, approvals, companies (new, decision 4)
packages/integrations ports, in-memory fakes, HTTP adapters for fake-providers, S3, SMTP, local KMS
packages/contracts    zod schemas, oRPC contracts, typed client
packages/documents    HTML templates, branded base layout, embedded fonts, SHA-256 fingerprint
packages/config       tsconfig bases, ESLint config and custom rules, Prettier
```

Conventions fixed now, because the team knows Fastify rather than NestJS (ADR-001):

- **Module shape.** Each NestJS module has `*.module.ts`, services, repositories (all queries; they take the transaction handle they are given) and its exported public service. Modules import each other only along the layers in architecture section 2; `eslint-plugin-boundaries` enforces the layers.
- **Ports.** Integration ports are injected by token (`SMS_PORT` and so on). Tests swap in the in-memory fakes; dev and e2e use the HTTP adapters against `apps/fake-providers`.
- **Custom lint rules** in `packages/config`: no role comparisons outside the policy module; no raw database client outside `packages/db` and the core module; no `parseFloat`, `toFixed` or `Math.round` outside `packages/domain/money`; no provider SDK imports outside `packages/integrations`; no I/O modules (`node:fs`, `pg`, HTTP clients) in `packages/domain`.
- **Tests.** Vitest everywhere except the Expo app. NestJS tests compile through SWC (`unplugin-swc`) for decorator metadata. Integration tests get a fresh database per Vitest worker, cloned from a migrated template database, so they run in parallel against real PostgreSQL with RLS on.

### 4.3 Database roles, migrations and company context

**Roles.**

| Role | Login | Purpose |
| --- | --- | --- |
| `rent_owner` | yes | Owns schemas, tables and `SECURITY DEFINER` functions; runs migrations and pg-boss's schema setup. Never used by the running apps. |
| `rent_app` | yes | The api and worker connect as this role. Not an owner, `NOBYPASSRLS`, no UPDATE, DELETE or TRUNCATE on append-only tables, EXECUTE only on named functions. |
| `ledger_writer` | no | Created now with no grants. M4a gives it INSERT on the journal tables (ADR-003). |

**Migrations.** One ordered folder in `packages/db/migrations`. Drizzle Kit generates table migrations from the schema; roles, RLS policies, triggers and functions are hand-written SQL migrations (`drizzle-kit generate --custom`) in the same sequence. `pnpm db:migrate` applies them as `rent_owner`. Cluster-level roles are created by an idempotent bootstrap script, used by the Compose init and by CI.

**Company context.** `withCompany({ companyId, personId, actorKind, requestId }, fn)` opens a transaction, sets `app.company_id`, `app.person_id`, `app.actor_kind` and `app.request_id` with `set_config(..., true)`, and passes the transaction handle to `fn`. Every API request and every job goes through it. Session-level `SET` is never used; a test proves that context does not survive on a pooled connection after the transaction ends.

**RLS template**, applied by a SQL helper to every company-scoped table:

- `ENABLE` and `FORCE ROW LEVEL SECURITY`.
- One policy for all commands, `USING` and `WITH CHECK` on `company_id = app.current_company_id()`. The function returns NULL when no context is set, so a query without context sees nothing (fail closed).
- `UNIQUE (company_id, id)` on the table, and composite foreign keys `(company_id, x_id)`.

**System paths** (ADR-002), each a `SECURITY DEFINER` function with a pinned `search_path`:

- `app.memberships_for_person(person_id)`: a person's companies and roles, for sign-in and the company picker.
- `app.company_ids()`: company ids only, for schedulers.
- `app.create_company(...)`: company onboarding, called only after `PolicyService` allows it (seed and CLI in M1, admin console in M10).
- `app.claim_outbox_events(limit)`: the outbox relay's cross-company read (4.11).

### 4.5 Authentication and sessions

Better Auth runs inside `apps/api` through `@thallesp/nestjs-better-auth` (supports NestJS 12 and Fastify), with the Drizzle adapter, UUIDv7 ids, and these plugins: two-factor (TOTP and backup codes), phone number, Expo, and database-backed rate limiting. The cookie cache is off, so a revoked session fails on its next request.

| User | Sign-in | Second factor | Idle timeout | Absolute timeout |
| --- | --- | --- | --- | --- |
| Owner, agency admin, manager, accountant, adviser | Email and password | TOTP, mandatory, no "trust this device" | 30 min | 12 h |
| Platform admin | Email and password | TOTP, mandatory | 15 min | 12 h |
| Caretaker | Phone code | the phone | 30 min | 12 h |
| Tenant | Phone code | the phone | 30 days (decision 6) | 180 days (decision 6) |

- **How timeouts work.** Better Auth's sliding expiry gives the idle timeout (refreshed at most once a minute). Our actor guard enforces the absolute limit from `session.createdAt` and the shorter platform-admin idle limit, and revokes the session when either is passed.
- **TOTP enforcement.** A staff member with any password role who has not enrolled TOTP can reach only the enrolment endpoints. Enrolment shows a QR code and backup codes once.
- **Auth method on the session.** Each session records `auth_method` (`password_totp` or `phone_otp`) and `active_company_id`. A phone-code session carries only the roles that may use phone sign-in (caretaker), so a person cannot use a phone code to act as a manager.
- **Phone codes.** 6 digits, 10 minutes, 5 attempts. Sign-in only for people who already exist (landlords create tenants; there is no self sign-up). An unknown number gets the same response and no SMS, which stops enumeration and SMS pumping. Sends are limited per phone (3 per 15 minutes) and per IP (10 per hour); these are security defaults in config, not law. Codes go out through the outbox and the SMS port.
- **Passwords.** Better Auth's default hashing, or argon2id if it can be configured; at least 12 characters.
- **Cookies and origins.** `apps/web` proxies `/api` to the API, so staff cookies are host-only (`__Host-` prefix, Secure, HttpOnly, SameSite=Lax) on the web origin. `apps/links` is a different host and never receives them. The Expo app keeps its session token in SecureStore. In production the Expo web build is served on the same origin as an `/api` proxy, decided at first deployment.
- **Audit.** Sign-in, sign-out, failed sign-in (where Better Auth exposes it), TOTP enrolment and removal, and session revocation are audited. They go to the chain of every company where the person has an active membership, or to the platform company's chain if there is none.

1. The NestJS integration works on the Fastify adapter, alongside oRPC controllers and our guards.
2. TOTP is enforced per role.

### 4.7 Approvals engine (AD-05)

- **Request.** An action type registers a handler: eligible approvers (through the policy service), a payload hash of the fields that matter, and `execute(tx, request)`. A request stores the action, subject, payload, payload hash, initiator, mode, required approvals (1 besides the initiator), expiry and status.
- **Decision.** Approving re-reads the subject and recomputes the hash. If it changed, the request is cancelled as `subject_changed`. Otherwise the decision row, the status change, `execute` and an `approval.approved` outbox event commit in one transaction, or nothing does. The request row is locked during a decision, so two approvers acting at once run the action once.
- **The database enforces the initiator rule.** A trigger on `approval_decision` rejects a decision by the initiator unless the request is in cooling-off mode, the decision is `self_confirm`, and the server time has passed `cooling_off_until`. It also rejects decisions on closed requests and duplicate deciders. Status transitions are checked by a trigger as well.
- **Single-user mode (OQ-29).** When a request is created and no eligible approver exists besides the initiator (nominated approvers count), the request enters cooling-off for 24 hours (the period in AD-05). After that, the initiator confirms with a fresh TOTP code. The decision is recorded as a self-confirmation after cooling off, and the audit log and any document produced say so. I chose TOTP over an SMS code because every user who can initiate these actions already has TOTP, and it costs no SMS.
- **Expiry.** Requests expire after a per-action-type period, 7 days by default (a product default I chose; not in the PRD). An hourly job closes expired requests.
- **M1 action types.** None in production. Tests register a test action type. Real types arrive with their milestones (section 3).

### 4.8 Audit log (AD-07)

- **Writing.** All writes go through `audit.append(...)`, a `SECURITY DEFINER` function; `rent_app` cannot insert into `audit_event` directly. The function locks the company's `audit_chain_head` row, computes `hash = SHA-256(prev_hash || canonical fields)` with pgcrypto, inserts the event with the next `seq`, and updates the head. The first event's `prev_hash` is 32 zero bytes.
- **Fields.** `seq`, `company_id`, `occurred_at` (server time, UTC), actor person, actor kind, request id, action, record type, record id, `data` (before and after, or the semantic payload), `prev_hash`, `hash`, `hash_version`.
- **Row triggers** on `company`, `membership`, `approval_request` and `rule` call the function with the before and after rows, taking actor and request id from the transaction settings. Encrypted and secret columns are recorded only as changed, never by value. A role or scope change on a membership is the "permission change" of the AD-07 acceptance criterion: who, when, before and after.
- **Semantic events** from services, for example `auth.signed_in`, `approval.self_confirmed`, `document.stored`.
- **Search.** `GET /audit-events` filtered by actor, record type and id, action and date range, newest first with keyset paging on `seq`. Indexes lead with `company_id`. Times show in the company's time zone.
- **Verification** (`audit.verify-chains`, nightly at 01:00). One job per company recomputes the chain in SQL with the same function, reports the first bad `seq` if any, and compares the head with the latest anchor. A mismatch raises an alert. Each run is recorded as an event in the platform company's chain.
- **Anchoring** (`audit.anchor-heads`, daily at 01:30). Writes each company's head (`seq`, `hash`, time) as a JSON object to the write-once bucket and records the object version in `audit_anchor`. This catches someone with database superuser rights who rewrites rows and recomputes every hash, because the anchored head will no longer match.
- **Contention.** The head lock serialises audited writes within one company until commit. Transactions are short, so this suits MVP volumes; the M11 load test checks it at month-end peaks. M4a decides whether journal lines get one audit event per entry rather than per line.

### 4.9 Rules engine and country configuration (TX-08, NFR localisation)

- **`rule` columns:** id, country, key, value (jsonb), `effective_from`, optional `effective_to` (set only at insert), source, `verification_status` (`verified`, `from_prd`, `unverified`), `verified_by`, `verified_at`, notes, `created_at`. Append-only.
- **Resolution.** `resolve(country, key, asOf)` takes the row with the latest `effective_from` on or before `asOf` (latest `created_at` breaks a tie) whose `effective_to`, if set, is not before `asOf`. It returns the value, rule id, status and source; callers store the rule id with what they calculated. A missing rule is an error, never a silent default.
- **Changes** are new rows. Verifying a value is a new row with the same value and date and status `verified`. Adding a row uses `pnpm rules:add` (needs a source and a status; `verified` needs a verifier). The admin console screen comes in M10.
- **Value schemas.** Each key has a zod schema in `packages/domain/rules`, for example `{ bps: 800 }` or `{ days: [21, 28] }`, checked on insert and on read.
- **Unverified flag.** `resolve` reports whether the value is unverified, so screens that use it (the notice composer in M7) can show the warning.
- **Seeds** (Ghana, from `CLAUDE.md` section 7). `effective_from` is 2000-01-01, a technical lower bound so imported history resolves. Each row's note says it is not a legal commencement date.

### 4.11 Outbox and jobs (ADR-005)

- **Outbox.** Business code inserts into `outbox_event` (company, type, payload, unique idempotency key) in its own transaction. An insert trigger sends `NOTIFY`.
- **Relay** (worker). Wakes on `LISTEN` with a one-second poll as fallback, claims a batch through `app.claim_outbox_events` (`FOR UPDATE SKIP LOCKED`), and enqueues each event in pg-boss inside the same transaction that marks it published, using pg-boss's per-call database option. Publishing is exactly once and delivery at least once. Several relays can run at once.
- **Job definition.** `defineJob({ name, schema, idempotencyKey, retry, handler })`. The runner validates the payload with zod, refuses one without `companyId`, and gives the handler `ctx.withCompany(fn)`, which is always scoped to the payload's company. A handler can open several transactions, so provider calls stay outside them. Retries use exponential backoff per job. Exhausted jobs go to a dead-letter queue and raise an alert through `AlertPort` (log plus email to an ops address, which is Mailpit locally).
- **Idempotency, twice.** A pg-boss singleton key, plus a unique constraint on the effect: the natural key where there is one, otherwise `processed_job`, inserted in the same transaction as the effect.
- **Schedulers.** pg-boss cron in Africa/Accra time. A scheduler job calls `app.company_ids()` and enqueues one company-scoped job each.
- **M1 jobs.** `outbox.relay`, `audit.verify-chains`, `audit.anchor-heads` and `documents.render-pdf` from the catalogue, plus two additions for architecture section 10:

| Job | Trigger | Idempotency key | Retries |
| --- | --- | --- | --- |
| `approvals.expire-requests` | hourly | request id + expiry | 3 |
| `identity.send-otp` | event: code requested | verification id | 3, within 1 minute (codes last 10) |

### 4.13 Storage, documents, PDF and fingerprints

- **Buckets.**
    - `files`: private and versioned, for uploads such as logos and later photos.
    - `evidence`: Object Lock enabled, for signed documents, rendered evidence and audit anchors. Writes use `If-None-Match: *`, so an object key is never replaced, and the database stores the version id with the SHA-256.
- **Retention.** Each evidence object gets an Object Lock retain-until date from the rules table (`data_retention.financial_and_notices`, 6 years, unverified). While the rule is unverified, the lock uses governance mode, which only a break-glass role can shorten (the app role cannot); once counsel verifies it, new objects use compliance mode. This replaces the legal hold in the first draft of this plan: the research supplied a value, and governance mode keeps it reversible. ADR-006 is amended to match.
- **Uploads.** Presigned POST with a content-type condition and a size limit per purpose (logo: PNG, JPEG or WebP, at most 1 MB). After upload, the API checks the object and the worker re-encodes images with sharp (strips metadata; logos become PNG at most 512 px wide). A `document` row then records the result. Downloads use 5-minute presigned GET URLs issued after a policy check.
- **Templates.** React components rendered to static HTML in `packages/documents`, each with a key, a version and a zod data schema. The base layout carries the company's logo, colours and sender name. Fonts are embedded (Noto Sans, which includes ₵, U+20B5). M1 ships the base layout and a sample template for tests.
- **Rendering** (`documents.render-pdf`). A warm pool of headless Chromium pages in the worker (Playwright). All network requests are blocked during rendering, so images arrive as data URIs. Output is A4 PDF. The PDF goes to the `evidence` bucket, then a `document` row and a `document.stored` audit event, both with the SHA-256.
- **Fingerprint.** SHA-256 over the final bytes, in `packages/documents`. A verify helper reads the stored version and compares.
- **Watch for M3.** ADR-006 names pdf-lib for certificate pages, and pdf-lib has had no release since 2022. M3 should confirm it still works or pick a maintained fork.

### 4.14 Field encryption, blind index and log redaction

- **Envelope encryption.** A KMS master key encrypts a per-company data key (`company_key`, versioned, rotated yearly). Values use AES-256-GCM with a random 96-bit IV, and the AAD binds each ciphertext to company, table, column and row id, so ciphertexts cannot be swapped between rows. Ciphertexts carry a version prefix and the key version.
- **Blind index.** HMAC-SHA-256 over the normalised value, with a per-company key derived by HKDF from an index master secret. Equal values in different companies get different indexes.
- **Masking.** Helpers mask values by default, for example `GHA-*******89-0`. The reveal flow (permission, reason, audit) arrives with tenant ID numbers in M3.
- **Redaction**, with two layers:
    1. pino `redact` paths for known fields: phone, email, code, otp, token, password, ID number, signature, authorization, cookie, body.
    2. A serializer that scrubs values anywhere in the log line: E.164 and local Ghanaian phone formats, emails, Ghana Card numbers, long base64url strings (tokens) and 6-digit codes in code-like fields.
- **HTTP logs** carry method, route template, status, duration and request id. They never carry bodies, query strings or raw paths, because link paths contain tokens.

### Deviations from this plan

1. **Better Auth is mounted directly on Fastify**, behind an endpoint allowlist, rather than through `@thallesp/nestjs-better-auth`. One guard path, and no body-parser changes.
2. **Phone sign-in codes are sent straight from the auth request.** The planned `identity.send-otp` job was dropped, so a plaintext code is never written to the outbox or the queue. The architecture's job catalogue is updated.
3. **Session limits live in `expiresAt`.** It is always the earlier of last activity plus the idle limit and creation plus the absolute limit, so Better Auth's own routes enforce both limits too.
4. **TOTP backup codes are encrypted at rest.** Better Auth's default stores them as plain JSON.
5. **Evidence retention is governance-mode Object Lock**, from the rules table (6 years, unverified). Compliance mode follows once counsel verifies the value. This replaces the first draft's legal hold.
6. **New migration `0003`:** `app.platform_company_id()`, so person-level audit events (a tenant's sign-in) go to the platform chain.
7. **Logos are re-encoded in the API request** (1 MB at most), not in the worker.
8. **Module layers are enforced by a custom lint rule** (`rent/module-layers`), not `eslint-plugin-boundaries`. The module map gained four same-layer imports, recorded in architecture section 2.
9. **No `nestjs-pino`.** A 30-line NestJS adapter over pino sends every line through the redactor.
10. **No shadcn/ui.** The web app has a few small Tailwind components of its own.
11. **The Expo app needs two changes for Hermes and pnpm:** a local entry file (`apps/tenant/index.js`), and a Babel transform for `@orpc` packages, because Hermes cannot parse their destructured rest parameters.
12. **`AUTH_RATE_LIMITS` switches Better Auth's per-IP limits.** Tests and the CI e2e job turn them off; the config refuses that in production.
13. **pnpm 12's minimum release age** made pnpm record exclusions in `pnpm-workspace.yaml` for the Expo 58 patch releases of 2026-10-28.
14. **Found during the build and fixed:**
    - The KMS context encoding was ambiguous; it now uses a JSON encoding.
    - GCM tag lengths were implicit; they are now explicit.
    - The PDF renderer leaked state between renders and could hang on a page close.
    - The in-memory SMS fake accepted non-E.164 numbers.
    - A non-JSON provider response threw a raw error instead of a retryable `ProviderError`.
